# Compiler

Status: accepted compiler architecture through execution, specialization, optimization, linking, diagnostics, reproducibility, and pure editor-preview JIT. Detailed IR instruction sets, individual pass designs, and build-tool packaging are implementation specifications rather than unresolved product policy.

## Compiler boundary

The host-native Rust compiler exposes one deep Module over a deterministic batch pipeline of immutable phase artifacts with explicit inputs. The command-line builder, tests, inspector, and graphical editor use that same Module instead of assembling independent compiler pipelines.

Its external interface has only two operations: `Compiler::open(CompilerInstallation)` seals one authenticated immutable Compiler Distribution, while `Compiler::compile(CompilationRequest, Cancellation)` runs one authoritative compilation. A Compiler instance owns no current Project, mutable workspace, semantic session, query engine, dependency invalidator, or persistent cache. The first implementation may serialize concurrent calls, but request order, thread count, prior cancellation, and private reuse cannot change canonical outcomes.

Every request carries a complete immutable Project snapshot containing every regular `.wr` file beneath the conventional `src/` directory as exact bytes under a canonical Project-relative path, together with recognized declared immutable content, revision identity, and a verified snapshot digest. Filesystem and editor-document adapters construct that snapshot before the compiler seam; the compiler never rereads ambient files during a request. The adapter rejects symlinks along recognized source paths and canonical path aliases, while absolute paths, timestamps, inode numbers, permissions, directory order, Git state, ignored files, environment variables, and unrecognized content never enter compiler semantics. `Analyze` is target-neutral and stops after source semantics. `Plan` carries an Architecture Profile, evaluates the Image Constructor, and validates the closed `ImagePlan`. `Build` additionally carries a build mode and produces the native Image. `Plan` and `Build` rerun their complete authoritative prefixes rather than accepting an Analysis, `ImagePlan`, or another phase artifact as input.

A compilation finishes as exactly one of `Accepted`, `Rejected`, `Cancelled`, `HostFailed`, or `Defect`. `Rejected` contains Creator-correctable structured diagnostics. `HostFailed` contains failures of required native tools, temporary storage, or other host prerequisites. `Defect` contains violated compiler invariants, malformed compiler-produced artifacts, failed verifiers, unknown backend helpers, and bounded reproduction evidence. No unsuccessful outcome contains an Image, and the compiler never disguises its own defect as a Creator error.

Rejected requests may expose only immutable artifacts valid before the hard error gate, such as lossless syntax and locally valid semantic observations. Cancelled requests expose no downgraded intent, resumable token, partial result, or publicly reusable cache entry. Cancellation is one-way operational control polled at compiler-owned bounded checkpoints; it is not a build input and cannot change any request that reaches an accepted or rejected canonical result. The synchronous Rust interface lets a host tool choose its own worker-thread policy without selecting an async runtime for compiler semantics.

An `InspectSelection` changes only which immutable semantic observations appear in the returned `InspectArchive`. Callers may inspect syntax, stable identities, Typed-HIR summaries, behavior facts, plans, costs, layouts, receipts, and Evidence Bundle data, but cannot select or skip passes, advance compilation, mutate artifacts, or feed an artifact into another request. Internal artifact types are valid only for the exact compiler build that produced them; only deliberately persisted contracts receive canonical versioned encodings.

The compiler may use controlled temporary storage and private native-tool adapters, but it accepts no output directory and performs no caller-visible persistence. Accepted artifacts carry their canonical identities and contents; the CLI or editor decides where to retain them. A caught unexpected host panic becomes a bounded `Defect`, poisons that Compiler instance, and requires the caller to reopen it before another request.

The initial Rust workspace exposes one public `wrela-compiler` library Module. Syntax, resolution, Typed HIR, the evaluator, diagnostics, and later IR phases remain private implementation modules. Consumer-level tests cross the same `compile` seam as real tools; narrow phase and verifier tests remain private to the implementation. A new public crate, daemon protocol, session interface, progress stream, inspection pager, or persistent artifact store requires a demonstrated second seam or measured editor need rather than speculative flexibility.

Project source cannot extend the compiler with plugins. The authenticated toolchain supplies a closed set of Image-kind and Facility planners. A Project selects and configures those planners through ordinary checked Wrela declarations and its Image Constructor.

Authenticated Wrela modules come from a compiler-distribution registry keyed by content digest, role, version, and permitted Compiler Primitives. Trust is not a source modifier or reserved pathname, and Project modules cannot shadow or forge registered module identities.

The compiler represents the evaluated declaration graph as a generic target-neutral `ImagePlan`. Trusted planners validate and refine their owned declarations without hard-coding Console, Display, Event Store, or individual Virtio devices into the generic compiler graph.

## Source and identity

Parsing produces an immutable lossless syntax representation suitable for exact source preservation, diagnostics, formatting, and future editor collaboration. Every source byte is owned exactly once by a token, trivia region, or invalid-token node, and an unedited tree prints byte-for-byte identically to its input. Recovery may create explicitly marked zero-width missing nodes but never invented source bytes. Syntax nodes have no durable identity across compilation requests. Semantic analysis uses a separate representation rather than progressively annotating or rewriting syntax nodes.

The Module closure begins at the only root source, `src/image.wr`. Other Modules are hierarchically nested, derive identity from canonical paths rather than source declarations, and are selected through the one absolute whole-namespace `from parent.path import leaf [as alias]` form without ambient filesystem reads. The Project snapshot digest covers all captured candidate source, while a separate semantic closure digest covers only the reachable Project Modules, their authenticated Module dependencies, and their exact origins. Editing unreachable valid source changes the snapshot revision without changing the semantic closure, accepted Image, or Image identity.

Missing roots, malformed Project paths, duplicate or colliding Module identities, declaration visibility failures, unresolved imports, and import cycles are Creator-correctable rejection. A host adapter's inability to capture selected bytes consistently is a host failure. Compiler invariant violations after accepting an immutable snapshot remain defects. Diagnostics and Evidence Bundles name canonical Project-relative paths and never expose absolute host locations.

Resolution assigns closure-wide semantic identities independently from semantic fingerprints and private artifact indexes. An identity answers which thing a semantic artifact represents; its fingerprint answers whether that thing still has compatible meaning; a request-local index answers only where one immutable artifact stores it. A declaration remains owned by its defining Module, and every monomorphized executable body has one canonical closure-wide `SpecializationId`. Source spelling, AST addresses, copied imported declarations, traversal ordinals, dense arena positions, and concatenated strings are never identities for named semantic declarations.

Every semantic identity begins from a versioned domain-separated canonical binary key with explicit tags, fixed integer encodings, and length-prefixed sequences. The initial identity schema uses deterministic XXH3-128 to give the key its opaque strongly typed external form, while the private interner retains the complete structured key and compares it on every insertion. Equal keys intern once; distinct keys with the same digest are a compiler `Defect`. The digest is an accelerator and compact observation, never the authority for semantic equality, cache reuse, or Source Transaction rebasing. The digest algorithm, canonical encoding, tags, and key schemas share one identity-schema version; changing any of them intentionally invalidates observations and artifacts without a compatibility promise.

One immutable compiler-owned `IdentityCatalog` is the deep Module for this bookkeeping within a compilation revision. It owns canonical-key interning and the correspondence among typed opaque IDs, readable names, provenance, and fingerprints. Compiler phases carry typed IDs and consult the catalog; they neither reconstruct identities nor maintain phase-specific identity dialects. Artifact-local indexes remain private to their owner, and inspection projects immutable observations rather than exposing catalog mutation or canonical keys as a public compiler seam.

Project `ModuleId` keys contain the Project-origin tag and structured canonical Module path, but no source bytes, absolute path, importer, alias, traversal order, or invented global Project identity. Authenticated Module keys additionally contain their registry and authenticated content identities. Project-origin IDs are meaningful only with their compilation and Project-revision context, so two unrelated manifest-free Projects may derive the same raw ID for the same Module path without becoming the same Project. Only the reachable closure receives semantic Module and declaration identities; captured unreachable files retain source identity and lossless syntax but remain semantically inert.

A `DefId` key contains its defining `ModuleId`, containing declaration chain, declaration kind, and declared name. One declaration namespace exists per Module and one member namespace per nominal type; Wrela has no overloading by kind or signature. Top-level declarations, fields, variants and their named payload fields, methods, associated declarations, interface requirements, generic parameters, and function parameters receive `DefId`. Import aliases and local bindings use resolution or body-local identities instead. Visibility, attributes, signature, body, documentation, and source position affect fingerprints and provenance rather than `DefId`.

Mutually exclusive arms of one compile-time conditional may declare the same owner, name, and kind as alternatives for one logical `DefId`; branch position does not enter its key. Different declaration kinds across those arms are rejected, and any configuration in which two same-key declarations can coexist is rejected deterministically as Creator-correctable ambiguity. The selected signature and implementation affect fingerprints. Independent conditional declarations may not reuse a key merely because a more elaborate proof might establish exclusivity.

Trivia, documentation, declaration order, signature, body, visibility, attribute, and field-type edits preserve a named declaration's identity while changing the relevant source or semantic fingerprint. Renaming it, moving it to another Module or owner, changing its declaration kind, or deleting it changes identity. A deliberate editor rename may record an old-to-new mapping only within that atomic Source Transaction and its undo history; Wrela adds no hidden source UUID or permanent alias to make the rename identity-preserving. Anonymous constructs such as closures, Panic sites, branches, expressions, and local bindings receive deterministic identities scoped to the enclosing definition revision; a body edit may invalidate them. Creator-facing durability requires a named declaration, Authoring Parameter, or another explicit domain identity rather than an invented stable source address.

Canonical `TypeId` keys distinguish fixed compiler-defined primitive tags from nominal and structural types. A nominal key contains its type declaration `DefId` and ordered canonical generic arguments; fields and members affect its fingerprint rather than its identity. Transparent aliases retain their own declaration identity and source provenance but normalize to their target `TypeId`. Structural keys recursively name array element and canonical length, ordered tuple elements, function parameter modes and types plus return, suspension, and declared effect ceiling, concrete Pool identity for ownership types, and interface identity plus representation kind for `any Interface`. Inferred effects, target layout, and optimization results remain facts or fingerprints rather than type identity. The currently admitted concrete family behind `any Interface` has a separate `FamilyFingerprint`, canonically ordered by concrete `TypeId` and required representation contract; family changes invalidate layout, cost, and code artifacts without changing the existential `TypeId`.

One closure-wide type interner owns every canonical `TypeId`; Modules never copy or re-key imported types. Nominal keys do not recursively expand their fields, so recursive semantic relationships do not make recursive encodings. Private `TypeIndex` values provide artifact-local arena access. Field or variant reordering preserves its named identities and nominal `TypeId`, but changes Semantic Fingerprints because Wrela's synthesized ordering and other declaration-order semantics change.

A named Pool receives `PoolId` from its Pool declaration `DefId`; a scoped Pool receives revision-scoped identity from its enclosing definition and creation site; a generic Pool parameter is owned by its generic declaration and substitutes to one concrete `PoolId`. Pool identity participates in ownership `TypeId` and Specialization keys but never becomes const Data.

Canonical compile-time arguments use evaluator-produced values rather than source expressions, so equivalent expressions intern once. Their encoding includes `TypeId` and exact ordered Data: fixed integer bits, Boolean or enum identity, nominal fields in declaration order, tuple and array elements, exact Text scalar sequence, exact Bytes, and compiler-defined Space, unit, and layout forms. Only Data with a total canonical `ConstKey` may determine Type or Specialization identity. Ordinary floats require an explicit bitwise or total wrapper; Resources, Capabilities, Actors, Facilities, and host identities are forbidden.

Every semantic definition that originated in source retains one primary file-aware definition span, while every resolved use retains its own use span and resolved identity. Moving text within the same defining Module updates provenance without changing identity; moving a declaration to a different Module changes both. Generated compiler structures retain provenance back to their semantic owner and the generator, planner, or lowering step that produced them.

Generic declarations are resolved and structurally validated before use. A reachable concrete combination of a generic `DefId` and compile-time arguments is demand-specialized, fully checked after substitution, and interned as one closure-wide `SpecializationId`. Wrela initially treats generics as checked templates rather than implementing a polymorphic Core IR, dictionary passing, or backend-owned specialization.

Applied semantic types receive `TypeId`, while every executable function or method body receives `SpecializationId`, including a non-generic callable with an empty argument vector. A Specialization key contains callable `DefId`, applied receiver `TypeId` when present, and ordered canonical type, const-Data, and Pool arguments. Generic parameter names, call sites, instantiation paths, source spelling, body fingerprints, inferred effects, Architecture Profiles, build modes, and selected compile-time branch do not enter the identity. The selected branch contributes to the implementation fingerprint, so one semantic application still has exactly one Specialization. A closure first receives a revision-scoped anonymous callable identity from its enclosing declaration fingerprint, construct kind, and deterministic structural ordinal, then uses the same Specialization machinery; captured runtime Data changes the closure value rather than its code identity.

All demand paths for one Specialization converge on one closure-wide interner entry and one checked immutable result. A deterministic worklist ordered by canonical identity handles discovery; recursive groups may refer to entries still being checked internally, but no partial placeholder escapes the phase. Generic diagnostics retain definition provenance, the deterministically ordered direct demand sites, one canonical shortest instantiation chain, and a bounded summary of alternatives rather than duplicating the same root failure for every caller.

The compiler computes the complete reachable `SpecializationId` set from the closed Image graph before Core lowering. Only that set participates in effects, ownership, capacity, cost, and code generation. Linker section collection is a defensive validation and size optimization, not the definition of semantic reachability.

Semantic Fingerprints form a tagged family rather than one universal digest. `SourceFingerprint` covers exact bytes, each declaration's `SignatureFingerprint` covers its resolved contract whether public or private, `ModuleInterfaceFingerprint` canonically aggregates the public declaration signatures and identities referenced by them, `ImplementationFingerprint` covers complete local resolved meaning, and `ArtifactFingerprint` covers one phase schema plus its declared input fingerprints. A Module implementation fingerprint canonically aggregates all selected declaration implementations, resolved import bindings, and compile-time selections. The closure fingerprint canonically aggregates reachable Module identities, origins, Module fingerprints, and dependency edges; unreachable captured source remains outside it. Every aggregate is canonically sorted rather than traversal-ordered.

Implementation fingerprints encode resolved identities, canonical literal and const values, parameter modes, ordered control flow and operands, ownership operations, and semantically active attributes; they exclude trivia, documentation, formatting, import aliases, redundant parentheses, source paths, offsets, and transparent-alias spelling. Declaration fingerprints remain local and reference dependency identities rather than recursively hashing a call graph. Phase artifacts explicitly record their direct input fingerprints and closure context, leaving dependency edges inspectable and avoiding recursive fingerprint fixpoints. Every persisted phase artifact also records the phase schema, identity-schema version, compiler semantic version, closure fingerprint, and direct input artifact fingerprints; an incompatible receipt causes a rebuild rather than compatibility adaptation.

Generated semantic definitions use a separate domain-tagged key containing generator identity, semantic owner identity, closed generated role, and deterministic role-local key. Synthesized standard capabilities, async resume functions, planner output, and later compiler glue cannot collide with source declarations and retain provenance to both owner and generator. Standard `Eq`, `Order`, `Hash`, and similar operations are generated definitions owned by their nominal type and closed capability role; concrete executable applications receive ordinary `SpecializationId`. A field change updates their fingerprints rather than inventing new identities. A generator implementation change likewise updates fingerprints; changing the stable role or owner changes identity. The compiler never fabricates source provenance for generated definitions.

`ModuleId` is assigned during closure discovery, source `DefId` during declaration collection, `TypeId` during resolution and typing, `SpecializationId` during concrete demand, and generated identities plus artifact-local indexes during lowering. Every downstream immutable artifact carries upstream identities instead of reconstructing them. Local bindings, blocks, values, and instructions use strongly typed deterministic indexes valid only with their owning definition or artifact; structural verifiers reject dangling, wrong-owner, and wrong-kind references as compiler Defects.

Well-formed declarations may receive revision-scoped identities and observations even when another declaration makes the request Creator-rejected, so diagnostics and editors can inspect valid islands. Malformed or ambiguous declarations receive no semantic identity, and no artifact from a rejected request becomes reusable without ordinary validation in a later accepted request. Duplicate-definition, conditional-conflict, and identity-collision reports sort by canonical key and provenance rather than parallel discovery order.

Compiler identities are never durable gameplay or production-storage identities. Store Identities, Event schema identities, Event Producers, Marks, and other persisted domain contracts use their own explicitly governed identities and production schema lock; source `DefId`, `TypeId`, and `SpecializationId` are not embedded as their compatibility contract. The host-selected workspace lineage scopes revision and Source Transaction comparisons operationally, but does not enter source syntax, `ModuleId`, or a manifest-level global Project identity.

## Representation stack

The compiler uses representations with narrow responsibilities:

1. Lossless syntax preserves what the Creator wrote.
2. `DeclarationGraph` records the reachable Modules, imports, namespaces, declaration identities and signatures, and compile-time alternative groups without copying source bodies into a resolved AST.
3. `SpecializationCatalog` records structurally valid generic templates, constraints, source-body references, and resolution environments. A template is a recipe for producing Typed HIR, not partially typed HIR itself.
4. Typed HIR records one fully concrete Specialization's resolved identities, types, places and values, ownership operations, effects, and source provenance.
5. Immutable fact and evaluation tables record selected conditions, constants, `FunctionFacts`, eligibility, evaluation results, and receipts without rewriting Typed HIR.
6. Core IR makes monomorphized control flow, values, ownership operations, Panics, and Wrela-specific optimization facts explicit.
7. Flow IR represents suspension, Actor Turns, Replies, Groups, cleanup, cancellation checkpoints, and statically planned async frames.
8. World and Transport IRs represent symbolic visual structure, spatial bounds, approximation contracts, acceleration structures, and field-evaluation plans.
9. `ImagePlan` represents the closed target-neutral system graph, Facility requirements, resource bounds, service obligations, and logical placement constraints.
10. Backend lowering turns admitted synchronous functions and Flow resume functions into Cranelift IR and then target machine code.

One private semantic-analysis Module owns signature typing, compile-time selection, template validation, concrete specialization, ownership and effect analysis, constant evaluation, and Typed-Program assembly. It may use mutable builders and deterministic worklists internally, but only immutable completed artifacts cross its seams. Body-level name resolution and typing occur together because fields, methods, operators, interfaces, and generic operations require type information; the compiler does not create a second fully resolved source tree for later phases to copy.

Typed HIR is a structured statement-and-expression tree rather than SSA, bytecode, or a control-flow graph. It preserves scopes, `if`, `match`, bounded loops, exact left-to-right evaluation, and source provenance while canonicalizing spelling-only distinctions. Calls name their resolved callable and retain argument evaluation order with each argument's parameter `DefId`; aggregate initializers similarly retain source evaluation order before placing results in declaration order. Places, reads, copies, moves, borrows, assignments, initialization, cleanup, checked operations, short-circuiting, `?`, `defer`, Panic, and suspension remain explicit semantic operations.

Every expression carries its `TypeId` and provenance; relevant nodes carry resolved semantic identities, place-versus-value classification, and ownership mode. Expressions, statements, patterns, scopes, and locals use strongly typed indexes owned by one body artifact and make no cross-edit stability promise. Typed HIR contains no missing node, error type, ambiguous reference, poisoned value, target layout, Architecture Profile, Cranelift type, ABI decision, or build-mode fact. A rejected request may expose an independent locally valid concrete body, but an invalid declaration has no Typed-HIR body.

All selected declarations in reachable Modules have their signatures checked. Non-generic bodies and constants are checked eagerly, while generic templates must be structurally valid using only their declared type, Interface, const, and Pool constraints. A demanded Specialization substitutes every argument, evaluates its compile-time alternatives, and produces one fully checked concrete body; a concretely invalid selected arm rejects before dead-code elimination even when later optimization could remove it. Unselected arms must remain syntactically valid and expose declaration shells sufficient for identity checking but do not undergo name, type, ownership, or effect checking in that environment.

Compile-time selection occurs at the narrowest concrete environment: once for a non-generic Module condition, per applied `TypeId` for a generic nominal member, and per `SpecializationId` for a callable body. A condition cannot depend on a declaration selected by its own alternative group, and selection-dependency cycles are Creator diagnostics. Exact source changes affect `SourceFingerprint`; a template fingerprint covers every potential alternative; a concrete implementation fingerprint covers the evaluated condition, dependencies, and selected arm. Evaluated results remain side tables keyed by semantic identity or `SourceSiteId`, so Core lowering can use them without erasing the original operation or provenance.

Core IR is intentionally Wrela-owned. It is the home for optimizations that depend on Wrela semantics, including ownership and Pool reasoning, bounds and capacity proofs, effect-aware specialization, whole-Image constant propagation, and transformations coordinated with World compilation. World and Transport IRs may perform domain-specific transformations before producing or specializing Core IR. Cranelift remains responsible for generic machine optimization, instruction selection, register allocation, and emission; it is not Wrela's semantic optimizer.

Flow IR is also Wrela-owned and survives until scheduler behavior has been made explicit. Cranelift receives ordinary non-suspending functions and generated resume functions; it does not define Actor, Reply, Group, cancellation, or deterministic scheduling semantics.

Generated runtime glue is represented as authenticated compiler IR or authenticated precompiled runtime modules. The compiler does not generate Wrela source and feed it back through parsing and whole-closure semantic analysis.

## Compile-time evaluation

The authoritative pure evaluator is one private deep Module that executes verified concrete Typed HIR directly. Conceptually its one operation accepts a verified `TypedProgram`, typed evaluation root, policy, and operational cancellation token, then returns a structured outcome and receipt. It exposes no stepping, mutable stack Interface, callback registration, phase runner, or host-value adapter. Explicit control, call, and value stacks replace host recursion, and Wrela introduces neither an Eval IR nor JIT-defined compile-time semantics.

One evaluator implements constants and generic const values under `Const` policy, Boolean compile-time branches under `Condition`, concrete semantic and test calls under `PureCall`, and the Image Constructor under `ImageConstruction`. Roots are typed const identities with concrete environments, typed condition sites, or concrete `SpecializationId` plus typed canonical arguments; raw syntax, host values, and arbitrary host function pointers never enter evaluation. Policy selects eligibility, result validation, and versioned limits but never changes language semantics. Architecture Profile and build mode are unavailable to conditions, constants, generic arguments, Typed HIR, evaluator operations, and Image Constructor behavior.

Eligibility is derived over the closed concrete call family, including every runtime closure and `any Interface` alternative. Constants and ordinary pure calls admit no Actor, Facility-runtime, Driver, clock, entropy, persistence, caller-owned Pool, protocol Resource, Capability, suspension, or other external effect. Image construction additionally admits Build Constructors. Possible Panic remains a separate fact. A rejection identifies the first forbidden operation, its provenance, one canonical shortest call chain, and a bounded summary of other demand paths.

Semantic `EvalValue` values are immutable and canonical; mutation occurs through private local cells and scoped storage, so Rust allocation and sharing are unobservable. Values retain exact Type, integer width and bits, specified float format and canonical NaN result, exact Text scalar sequence, declaration-ordered aggregate content, concrete closure identity plus captured Data, and concrete existential representation. Calls dispatch through resolved `SpecializationId`, never a Rust closure, host virtual call, reflection, or name lookup. Const-policy results must additionally satisfy the total `ConstKey` rules.

A pure root may create a statically bounded scoped Pool when its identity, capacity pressure, mutation, and ownership remain entirely local. Evaluator-local Pool identity derives from root, source site, and invocation path; allocation, generation-checked Keys, moves, reclaim, capacity, `?`, return, ordinary scope exit, and reverse-order `defer` follow Wrela semantics. Panic performs no source cleanup. Compiler cancellation, evaluator exhaustion, and compile-time Creator rejection discard private evaluation state without pretending source cleanup executed.

Build Constructors are sealed pure operations implemented as closed compiler-owned cases and exposed through authenticated Wrela declarations. They create immutable typed symbolic graph nodes and handles in evaluator-private storage without ambient mutation or Facility-specific planning. Only nodes reachable from the returned Image root enter the graph; graph handles may form static cycles and follow their declared Data or Resource modes, but cannot become const Data, cross evaluation roots, support equality, ordering, hashing, or serialization, or escape the sealed graph. Each node receives a revision-scoped `ConstructionId` from Image Constructor identity, construction role, source site, canonical helper-call path, and deterministic loop or recursive coordinates. This identity supports wiring, planning, diagnostics, and identical builds, not persistence across source refactors.

Build Constructors validate only constraints local to their typed operands. After successful evaluation, a generic graph sealer checks one root, ConstructionId uniqueness, same-root handles, cycle-safe reachability, ownership, legal wiring, and complete construction-only Resources. Creator-authored invalid construction is `Rejected`; an impossible malformed value or verifier invariant is `Defect`. Facility-specific planners consume the sealed graph afterward and never execute as evaluator callbacks.

Every evaluated loop already carries a compiler-derived finite maximum, and every recursive cycle carries a recognized decreasing bounded measure. Wrela has no `@budget` trust assertion or evaluator option that can make unbounded work legal. A later admission design may let Creators state ceilings that constrain an independently proven bound, but evaluator fuel remains compiler containment rather than semantic proof.

Evaluation uses one versioned logical tariff model with fixed policy-specific per-root fuel and peak-memory ceilings plus deterministic compilation-wide fuel and retained-value ceilings. Operations, frames, locals, aggregates, Text and Bytes, scoped Pools, and symbolic declarations have logical charges independent of elapsed time and Rust allocation size. Named constants evaluate once per concrete environment, ordinary calls charge each execution, and general call-result memoization is initially absent; later private caching must reproduce the uncached logical charge and outcome. Forward constant references are allowed, actual selected dependencies determine demand, and re-entering an evaluating constant reports one canonical dependency cycle.

Constants, conditions, Specializations, fact fixpoints, aggregate usage, diagnostics, and artifact publication commit in canonical identity order. Independent calculations may run concurrently only when thread count and host scheduling cannot change acceptance or observations. All selected non-generic constants and unconditional Module-level compile-time assertions evaluate during `Analyze`, even if otherwise unused; generic associated values evaluate for demanded environments. The Image Constructor, pure-test suite, graph sealing, and executable lowering wait behind the complete reachable semantic no-errors gate.

Evaluation outcomes are `Completed`, `CreatorRejected`, `Panicked`, `LimitExceeded`, `Cancelled`, or `Defect`. Creator rejection has closed diagnostic kinds including failed compile-time assertion and locally invalid Build Constructor input. An ordinary `Result.Err` is a completed Wrela value. Structured failure carries root, provenance, relevant identity, bounded canonical call chain, and for exhaustion the policy, ceiling, usage, and deterministic top contributing sites. The caller maps these facts by purpose: build-time rejection becomes compilation `Rejected`, the same pure-call outcome may be a structured test failure, cancellation remains cancellation, and a Defect can never be presented as a Creator error. Evaluation performs no host operation and therefore cannot produce `HostFailed`.

Each semantic result fingerprint describes only its canonical value or structured failure. Its separate evaluation receipt additionally names the Typed-HIR fingerprint, root and arguments, eligibility facts, policy and tariff schemas, dependency roots, actual fuel, and peak memory. Tariff changes may alter receipts without altering completed Wrela values. Exact tariffs and ceilings are published Compiler-Distribution implementation specifications with conformance tests, not source syntax or compatibility promises. Evaluation receipts and results are output-only facts rather than reusable compilation inputs.

Compile-time and compiled ordinary floating-point operations share one specified mode: round to nearest with ties to even, preserve signed zero, use no ambient host floating-point mode, and canonicalize NaN results. Transcendental functions are not inherited from the host math library; each may be added later only with explicit language semantics and matching evaluator and runtime implementations.

## Behavior facts and optimization

Effects, possible Panic, suspension, ownership transfer and cleanup, allocation behavior, nondeterministic authority, boundedness, evaluator eligibility, and cost remain separate analyses with their own rules. `FunctionFacts` are derived from verified concrete Typed HIR through deterministic call-family fixpoints and keyed by stable identity; this aggregation is not a universal effect lattice. A declared `pure` ceiling is checked against inferred facts and cannot manufacture eligibility. Message ordering belongs to Flow analysis, and contextual machine or visual cost may be computed separately rather than forced into every function summary.

Core transformations preserve source-observable authoritative values, effects, ownership, deterministic choices, ordering, and possible Panic outcomes. A proven-impossible check may disappear; a pass may not introduce, defer, or reorder observable failure. Flow transformations additionally preserve Actor and scheduler observations. World and Transport transformations may approximate presentation only through an admitted Visual Contract.

Typed HIR's closed semantic operation set is authoritative for verification, evaluation, and Core-lowering obligations. Each operation defines operand and result typing, evaluation order, ownership modes, and possible Panic; adding one requires exhaustive evaluator, lowering, inspection, and differential-test support rather than falling through to a host operator or backend helper.

Typed HIR, Core IR, Flow IR, World and Transport plans, `ImagePlan`, and backend inputs each have structural verifiers. Every verified artifact names its phase schema, fingerprint, exact Identity Catalog revision, and declared input receipts behind a private unforgeable verified marker. The Typed-HIR verifier independently checks resolved-operation operand and result types, scope and control targets, ownership flow, effect and Panic facts, source ordering, and provenance ownership without repeating parsing, name lookup, or inference. A source mistake is diagnosed while constructing the artifact; a verifier failure, mixed catalog, dangling reference, or malformed compiler-produced artifact is a `Defect`.

Test and debug builds verify after individual transformations; release builds verify major seams. Generated eligible pure programs compare exact canonical Data, return alternative and payload, Panic kind and site, and left-to-right failure order between evaluator and optimized compiled execution. Evaluator fuel, stacks, private node IDs, native layout, instruction counts, and time are not semantic comparison targets. Build Constructors have no runtime counterpart and are tested against evaluator and graph-sealer invariants instead. Wrela does not require formal proofs or an optimizer-wide model checker.

Inspection exposes semantic identities and fingerprints, resolved call and reference relationships, source-site types and ownership modes, FunctionFacts, eligibility, outcomes, and receipts. It does not serialize private HIR arenas, local indexes, evaluator stacks, Rust variants, or a reusable `.hir` artifact. `DeclarationGraph`, `SpecializationCatalog`, `TypedProgram`, and evaluation-table artifacts remain private in-memory products of the exact compiler build; exact test discovery, stable diagnostic codes, and public test-observation schemas belong to their dedicated compiler-seam decision.

## Layout domains

The compiler keeps three layout domains distinct:

- **Wire Layout** is a portable exact byte contract for persistent Events, Store Snapshots, messages or protocols that explicitly request it, and other schema-governed data.
- **Logical Image Layout** is the target-neutral bounded arrangement of Pools, Mailboxes, async frames, buffers, Facility state, scheduler structures, and memory regions required by an `ImagePlan`.
- **Target ABI Layout** is the target-specific calling convention, stack and register representation, alignment, relocation, and machine encoding used by Cranelift and the selected machine serializer.

Crossing between layout domains requires an explicit checked lowering. A native struct layout never silently becomes a Wire Layout, and a Cranelift ABI choice never changes an Event schema or target-neutral capacity proof.

## Pipeline, diagnostics, and artifacts

Parsing, name resolution, typing, pure evaluation, monomorphization, proof analyses, World compilation, Image planning, cost analysis, and backend lowering consume and produce immutable artifacts through explicit stage interfaces. Global mutable compilation switches and duplicated frontends are forbidden.

Wrela initially implements this as a batch pipeline without a general query engine, dependency invalidator, in-memory incremental-recomputation promise, persistent cache, public progress stream, or revisioned compiler session. Stable identities and explicit inputs preserve the option to add those mechanisms when the editor creates a measured need. Any future reuse must be observationally equivalent to a fresh request with the same compiler executable and declared inputs; the batch build remains authoritative.

Lexing preserves invalid UTF-8, invalid characters, and malformed literals as invalid tokens with diagnostics rather than aborting. Parsing recovers at closing delimiters, line boundaries, dedents, and recognizable declaration starts without inventing indentation structure. Structurally valid declaration islands may lower independently even when other declarations in the same source are malformed. A malformed declaration remains syntax-only, and error values, missing nodes, and placeholder types do not propagate into semantic representations, the evaluator, Core IR, World compilation, Image planning, or backend representations. A hard no-errors gate precedes executable planning. Each file reports at most 64 syntax diagnostics followed by one explicit truncation diagnostic, while its complete syntax remains inspectable. IDE-grade typed holes and cross-file recovery are deferred.

Source ranges use request-local source identity plus authoritative half-open byte offsets. Human line and column locations are derived views; protocol-specific encodings such as UTF-16 editor positions belong in host adapters. Durable semantic declaration identities are defined independently of ephemeral syntax nodes.

Creator diagnostics and compiler defects are disjoint. A violated compiler invariant produces a structured internal compiler error containing the failed phase, stable artifact identities, and bounded reproduction evidence, and no Image is emitted. The compiler never disguises its own defect as a Creator source error.

Every important phase can emit a structured inspect artifact for reports and tests. These observations describe stable semantics and plans rather than promising compatibility for incidental Cranelift IR, register allocation, instruction bytes, or final Image byte offsets.

Anonymous source observations use a revision-scoped `SourceSiteId` owned by their enclosing declaration. A specialized Panic site combines that source site with its concrete `SpecializationId`. The compiler canonically sorts all reachable full identities and assigns compact Image-local ordinals in separate kind-specific tables; the Image carries an ordinal plus its kind while the Evidence Bundle, keyed by Image digest, maps it to full identity, Project-relative provenance, symbols, layouts, plans, and phase receipts. The Image profile selects each table's compact width and the compiler proves capacity. Compact ordinals are stable for repeated identical builds but may change with the reachable set and have no meaning without the Image digest. Evidence excludes absolute host paths and need not embed complete source text into the Image. The public `.wrela-image` container holds its Architecture Profile, Device Manifest, admitted RAM layout, bootable ELF, and any required architecture-owned reset member.

## Native backend and linking

The first compiler is AOT-only. It lowers admitted synchronous functions and Flow resume functions to Cranelift and emits standard target ELF object files through Cranelift's object module. Authenticated runtime and target-stub objects use the same link seam.

Backend and linker symbols derive from full `SpecializationId` or generated identity. A readable sanitized suffix may aid debugging but has no semantic authority, and any textual collision is a compiler Defect. Cranelift handles and backend-local numeric symbol indexes remain private implementation details.

Each Architecture Profile declares a fixed ISA, CPU-feature baseline, conventional freestanding calling convention, Cranelift version and flags, VM ABI revision, and trusted architecture stubs. Code generation never detects or inherits features from the compiler host. The initial compiler uses the architecture's conventional ABI across generated code and trusted stubs rather than defining a custom Wrela calling convention.

Safe runtime policy, Facilities, and Drivers are implemented primarily as authenticated Wrela modules. Minimal architecture-owned Rust or assembly stubs contain reset, interrupt and fault entry, MMIO, context switching, and operations that cannot be expressed through safe Wrela and Compiler Primitives.

A closed primitive manifest maps each typed Compiler Primitive to its exact Image-internal symbol, calling convention, required Capability-bearing operands, and permitted Architecture Profiles. Neither Creator nor authenticated Wrela source can declare a general FFI or acquire authority merely by naming a linker symbol.

An Image links no libc, libm, host operating-system library, shared library, dynamic library, or other external library. When Cranelift requests a helper operation, the backend must lower it directly or resolve it to a finite allowlisted sealed function owned by the Image runtime. Every requested helper appears in build evidence, an unknown helper is a compiler error, and the final linked result must contain no unresolved symbols.

A locally installed `ld.lld` links those objects under a compiler-generated, architecture-owned linker script. The compiler selects the explicit `ld.lld` executable name rather than a host-default `ld`, resolves it through the developer's `PATH` only when `Build` needs it, records its resolved path and reported version in build evidence, and reports absence or invocation failure as `HostFailed`. The linker resolves Image-internal symbols, applies relocations, places ELF sections, and reports overflows. ELF exists only as a host-side linking and QEMU-loading interchange: a small Wrela packager validates its linked segments against the Logical Image Layout and VM ABI, adds the Architecture Profile, Device Manifest, exact admitted RAM layout, and any architecture-owned reset member, and produces the final `.wrela-image` container. The guest does not contain an ELF loader. Wrela does not initially implement a general linker or private relocatable object format.

The current developer checkout has no external-tool setup operation or lock. It does not hash native tools, traverse their dynamic dependencies, inspect code signatures, bind them to a macOS build, or detect upgrades. Downloading, vendoring, authenticating, signing, and distributing a self-contained toolchain are one later product problem and must be designed together when Wrela is distributed beyond its builders.

Cranelift JIT is admitted only for compiler-produced effect-free Preview Kernels used by the graphical editor. It is not the semantic oracle, a general Wrela host target, deployed Image execution, an Actor or Facility runtime, a Driver environment, or part of scheduler semantics. Preview Kernels expose no host-call seam or ambient authority and are differentially checked against the Typed-HIR evaluator and scalar presentation semantics. They execute in a replaceable child Preview Worker so generated-code failure does not share the editor address space. All complete Images remain AOT-only.

## Reproducibility

Repeated builds using the same compiler executable, declared inputs, Architecture Profile, authenticated planner and runtime objects, Cranelift version and flags, unchanged local `ld.lld` installation, and build mode produce bit-identical Image bytes and canonical structured reports. Artifacts exclude timestamps, absolute host paths, host scheduling order, and unordered iteration.

Rebuilding an identical compiler executable from source across different hosts or across changes to locally installed native tools is a future toolchain-distribution and reproducibility problem. Wrela does not promise byte identity across compiler versions, Cranelift versions, LLD installations, build modes, or target architectures.

Development and optimized build modes preserve identical language, ownership, Panic, floating-point, and scheduler semantics. Neither may bypass resource, ownership, scheduler, deadline, or VM ABI proofs. A development Image may carry instrumentation and lack flagship performance certification, provided the Evidence Bundle says so explicitly; a development-only behavior is never valid evidence for a release-only semantic rule.

## Wrela8 inheritance

Wrela9 preserves the useful semantics and behavioral cases from Wrela8's lexer, grammar, type/access/move/flow analyses, whole-closure proofs, deterministic compile-time values and quotas, explicit async state-machine concepts, final artifact validation, and phase inspection. Each relevant case is inventoried and explicitly adopted, revised, or retired; none is binding merely because Wrela8 implemented it.

Wrela9 rewrites Wrela8's string-based identity, imported-body splicing, per-module generic ownership, recursive compile-time interpreter, closed product-specific `ImageGraph`, generated-runtime-source feedback loop, orchestration monolith, thread-local options, fragmented diagnostics, custom general-purpose optimizer, custom register allocator, AArch64 emitter, and linker relaxation. Wrela8's old intermediate and machine dumps remain migration evidence, not Wrela9 compatibility requirements.
