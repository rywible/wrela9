Throwaway logic prototype

Can a local lock catch toolchain drift without certificates or a bundled toolchain?

This demo models setup and verification for explicitly installed QEMU and LLD on Apple Silicon macOS. It tests whether paths, symlinks, binary hashes, dynamic dependencies, and the macOS system closure can produce useful failures without making Homebrew or signing part of Wrela.

    Facts observed on this Mac

    • /opt/homebrew/bin/qemu-system-aarch64 is a symlink to Homebrew QEMU 11.0.2. Its recursive Mach-O closure contains 29 non-system files and 27 system install names.
    • /opt/homebrew/bin/ld.lld is a symlink to Homebrew LLD 22.1.8. Its tiny launcher loads six LLD libraries, LLVM, and Z3: nine non-system files and six system install names in total.
    • Both executables are ad-hoc signed. Their complete file hashes already cover those embedded signatures; certificate trust adds no useful identity here.
    • Most macOS libraries live in the dyld shared cache rather than independently hashable files. The prototype therefore locks their install names together with architecture and exact macOS build.
    • QEMU ships a large firmware and data directory. Wrela's firmwareless invocation should select every runtime resource explicitly; installed-but-unselected QEMU data should not enter the lock.
